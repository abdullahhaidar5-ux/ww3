# net-1103 — online battle reliability (helper, 2026-11-03/04)

Abdullah asked (2026-11-03) to make online battles more reliable. Branch `orch/net-1103`.

## What changed (plain words)

1. **Mountain Fortress garrison survives a host takeover.** When the battle moves to another player (or the Cloudflare
   server picks a battle back up), the troops waiting inside the fortress — and inside tunnels and city buildings —
   come back with their proper unit stats, and a unit that stepped inside at the exact moment of the save is no longer
   saved twice (once outside, once inside). Clients already get the fortress count (`fn`/`fk` in the team panel), which
   the new host computes from the restored `b.gar`. (`src/07b-ckpt.js`: off-map units share the stat table `$s`;
   `ckEncode` skips `inTun` entities; `ckDecode`/`ckRestore` share one decoder.) Checked in `orch/ewtest.mjs` (new
   check: 3 units in a fortress -> checkpoint -> restore -> same kinds, real stat blocks, all come out alive).
2. **Nobody-took-over race.** A standby whose first try at opening the follow-up room timed out could, on its next
   try, find the room "taken" — by its own abandoned attempt — and then gave up for good, leaving no one to take over.
   For 30 s after one of its own timeouts, "taken" now means "try again". (`promoteToHost`.)
3. **Cloudflare server can't hang on its budget check.** Picking a battle back up after a server restart waits on the
   Budget object; if that call never answered, every player's reconnect waited behind it forever (the logged CI
   failure of 2026-10-29: both pages stuck 110 s, no /battle request ever completed, no takeover). Budget calls now
   give up after 8 s, which leads to the designed fallback (battle handed to the standby player).
   (`server/src/index.js` `budgetCall`.) Needs the `servers-live` deploy.
4. **Reconnect = full correct state (P1).** The code path (hostRejoin: fresh keyframe, team panel cache reset, collapsed
   city blocks re-sent, ack of pending orders) was already right for browser-hosted battles (mpsync `--reconnect`
   strict check passes, also over the new lossy network). `orch/cfclient.mjs` step 4 now does the full sync check
   after the friend reconnects to a Cloudflare battle (its side matches the server's checkpoint, both pages agree),
   not just a unit count.
5. **New test mode: `node orch/mpsync.mjs --lossy`** — browser-to-browser over a bad mobile network, in real time:
   120 ms one-way latency ±60 ms jitter, 3% of messages resent 250–750 ms later (links are reliable+ordered, so
   everything behind waits), a ~0.9 s lag spike every ~20 s; tune with `--lat --jitter --loss`. Same strict checks +
   reconnect. Runs in the ship gate's `mpsync` job (`--minutes 2`). Local results: default PASS (lag max 0.70 game-s,
   avg delay 207 ms, worst 1.1 s); harsh `--lat 220 --jitter 100 --loss 8` PASS (avg 372 ms, worst 1.3 s), all settle
   checks exact (0 missing / off / mismatched, credits equal).
6. **`migrate.mjs` "client fell N game-s behind".** Root cause is the test: it runs the battle 10–25x faster than real
   time, so a few hundred ms of real hiccup (GC, busy CI machine, a message through the local relay) read as many
   game-seconds (the CI log of 82043c0851 shows a clean takeover and exact settle checks, then "fell 7.5 game-s
   behind"). The client now waits up to 400 ms real time for the host's latest update each step (same as mpsync
   `--server`); a client the host really stops updating still fails at once.

## cfclient flake — what is known

Locally `cfclient` passed 3/3 (one run with an extra CPU hog). The only kept failure log (d136254, 2026-10-29) is the
server-restart hang above (fix 3). The cycle-19 failure's log was overwritten by its rerun; fix 2 is the only code
path found that makes "no player took over" permanent. If it recurs, `gate-logs/<sha>-cfclient` keeps the log.
